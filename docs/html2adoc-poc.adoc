= HTML to AsciiDoc: pandoc against a converter of our own
:toc: left
:icons: font

The export turns Confluence storage format into AsciiDoc in two steps.
`ConfluenceConverter.fixBody` prepares XHTML, and something then writes AsciiDoc from it.
That something has always been pandoc, started as a child process.

`html2adoc` is a proof of concept for doing it in process, seeded from the `html2adoc` module of https://github.com/jmini/asciidoctorj-experiments[asciidoctorj-experiments].
`HtmlToAsciidoc` puts both behind one interface, and `confluence.export.converter` picks between `pandoc` (the default) and `native`.

This page is the measurement.
A proof of concept that cannot be compared against what it would replace proves nothing.

== How this was produced

`ConverterComparisonSpec` runs both converters over every file of `html2adoc/src/test/resources/corpus`, applies `AdocOutput.substitute` to each result - which is what an export does next - and leaves both answers in `dtc-confluence-core/target/html2adoc-comparison`:

[source,bash]
----
./mvnw -pl dtc-confluence-core test -Dtest=ConverterComparisonSpec
----

Every output quoted below is from that directory, and every verdict below was checked by rendering both variants with `asciidoctor` and comparing the HTML.
That matters, because several of the differences look alarming and render identically, and two that look cosmetic do not render at all.

Where an output is quoted in part, the omission is marked with a comment line.
Nothing is cut silently.

=== The corpus

Six pages, which are the XHTML `fixBody` produces for the storage format this project itself publishes; `corpus/INVENTORY.md` records where each comes from and what it contains.
The corpus is small and it is not a sample of the world: it is what our own publisher writes, which is the input the export has to survive first.
Constructs it cannot speak about are listed at the end.

=== What the renderer says about the whole set

Both converters produce AsciiDoc that `asciidoctor` accepts without a single warning or error on all six pages.
The differences are therefore not in validity but in what is rendered.
Counted below from the rendered HTML of each page, with the `== <title>` line the export puts above it, where *p* is pandoc and *n* native:

[cols="3,1,1,1,1,1,1",options="header"]
|===
|Page |Links (p) |Links (n) |List items (p) |List items (n) |Images (p) |Images (n)

|`smoke-subpages-0-…Smoke_Test` |0 |5 (2 broken) |3 in 2 lists |3 in 1 list |1 |0
|`smoke-subpages-1-First_Page` |0 |2 |3 in 2 lists |3 in 1 list |0 |0
|`smoke-subpages-1-Second_Page` |0 |3 (2 broken) |0 |0 |1 |0
|`smoke-subpages-2-First_Page` |0 |2 |3 in 2 lists |3 in 1 list |0 |0
|`smoke-subpages-2-Subsection` |0 |0 |0 |0 |0 |0
|`smoke-subpages-1-…Smoke_Test` |0 |0 |0 |0 |0 |0
|===

Both converters render the list title and the table header row on every page that has one, so neither appears above.

Read in one line: the native converter is the only one that produces working links at all, pandoc is the only one that produces images, and the lists differ in nesting rather than in how many items reach the page.

== Page by page

=== smoke-subpages-1-docToolchain_Confluence_Smoke_Test.html

The root page of a split, and the smallest input: one paragraph whose text contains a newline.

[source,html]
----
<p></p><p>Generated by docToolchain against Confluence Data Center 9.2.21 (ASF cwiki).
This page exists solely to exercise the publishing pipeline.</p>
----

pandoc:

[source,asciidoc]
----
Generated by docToolchain against Confluence Data Center 9.2.21 (ASF cwiki).
This page exists solely to exercise the publishing pipeline.
----

native:

[source,asciidoc]
----
Generated by docToolchain against Confluence Data Center 9.2.21 (ASF cwiki). This page exists solely to exercise the publishing pipeline.
----

Both render one paragraph with identical text; AsciiDoc joins consecutive lines.
pandoc is nonetheless the better answer: `--wrap preserve` keeps the line break the author typed, and the author typed it after a full stop.
One sentence per line is the convention this project writes AsciiDoc by, and pandoc preserves it where native collapses it.

What native cannot do yet: keep a line break that carries no meaning to the renderer but carries meaning to the next person editing the file.

=== smoke-subpages-2-Subsection.html

A code macro and an admonition, both already reduced to placeholder tokens by `fixBody`.

[source,html]

<p></p><p>
</p><div class="content">
    <div class="code-wrapper">
    %%SOURCE-BEGIN%%groovy%%SOURCE-END%%%%CRLF%%

</div>
<p></p>
<p>%%ADMON-BEGIN-NOTE%%</p>

An admonition block, to check the storage format conversion.

<p>%%ADMON-END%%</p>
----

pandoc:

[source,asciidoc]
------
[source, groovy]

----

def hello = "world"
println hello

----

[NOTE]
====

An admonition block, to check the storage format conversion.

====
------

native:

[source,asciidoc]
------
[source, groovy]
----
def hello = "world"
println hello
----

[NOTE]
====

An admonition block, to check the storage format conversion.

====

The admonition is identical.
The listing block differs: pandoc keeps the literal newlines of the HTML as blank lines inside the delimiters, native does not.

Rendered, the two are the same - `asciidoctor` strips leading and trailing blank lines from a listing block - so this is a tie on output and a win for native on source legibility only.
The placeholder tokens survive both converters verbatim, which is what `AdocOutput` needs.

This is also the page where the native path marks the `div.code-wrapper` as a `<pre>` before converting, so that the sample inside the `----` lines is not escaped as prose.
The corpus cannot show the difference - `+def hello = "world"+` has no character that escaping would change - which is why it is specified in `PreformattedSpec` and `ExportConverterChoiceSpec` instead of counted here.

What native cannot do yet: nothing on this page.

=== smoke-subpages-2-First_Page.html

[source,html]

<p></p><p>A paragraph with <strong>bold</strong>, <em>italic</em> and <code>monospace</code>.<sup class="footnote">[

[[__footnoteref_1]]
xref:../docToolchain++_++Confluence++_++Smoke++_++Test/First++_++Page.adoc++#__++footnotedef++_++1++[++1++]++ ++]++

----

native:

[source,asciidoc]
----
A paragraph with *bold*,_italic_ and `monospace`. ^[^

[[__footnoteref_1]]
xref:../docToolchain_Confluence_Smoke_Test/First_Page.adoc#__footnotedef_1[1] ]

.A list
* First item


* Second item

* nested

'''

[[__footnotedef_1]]
Footnote xref:../docToolchain_Confluence_Smoke_Test/First_Page.adoc#__footnoteref_1[1] . A note belonging to the first page.
----

Four differences matter here, and they do not point the same way.

*The footnote links. Native is right.*
pandoc escapes every underscore, bracket and hash wherever it stands, so what reaches the document is no longer an `xref:` directive but this:

[source,asciidoc]
----
xref:../docToolchain++_++Confluence++_++Smoke++_++Test/First++_++Page.adoc++#__++footnotedef++_++1++[++1++]++ ++]++
----

`asciidoctor` renders that as the literal string:

[source,html]
----
<p>xref:../docToolchain_Confluence_Smoke_Test/First_Page.adoc#__footnotedef_1[1] ]</p>
----

Native passes it through, and the same input renders as a link:

[source,html]
----
<p><a href="../docToolchain_Confluence_Smoke_Test/First_Page.html#__footnotedef_1">1</a> ]</p>
----

This is not a matter of taste.
Every footnote link in every exported page is dead on the pandoc path today, and works on the native one.

*The list. pandoc is right, on nesting alone.*
Both converters render the title and all three items; the nested `ul` is where they part.
Native writes it at the same level as its parent, so `nested` becomes a third sibling of `Second item` instead of its child - one `<ul>` of three items against pandoc's two nested lists.
The blank lines between native's items are noise rather than an error: AsciiDoc keeps blank-separated items in one list, and the rendered HTML has the same three `<li>` either way.

*The space before `+_italic_+`. pandoc is right.*
Native writes `+*bold*,_italic_+`, which renders as `bold,italic` - the space the author typed is gone from the page.
`TextNodeConverter` trims each text node and then re-adds a space only when the last character matches `+[a-zA-Z0-9.:/()]+`; a comma is not in that set, so the trailing space of the text node `", "` is dropped and never replaced.

*The thematic break and the duplicate anchor. Neither.*
Native writes `'''` and pandoc `'''''`; both render as `<hr>`.
pandoc writes a second anchor from the `id` attribute of the footnote `div` (`+[[_footnotedef_1]]+` beside `+[[__footnotedef_1]]+`), native writes only the one the token asked for.
That is noise rather than an error, except that `asciidoctor` then gives the element the *second* id, so pandoc's rendered anchor is `+_footnotedef_1+` while the `xref:` in the document names `+__footnotedef_1+` - a second reason the pandoc footnotes would not resolve even if they were links.

What native cannot do yet: nested lists, and spacing around punctuation that is not in its whitelist.

=== smoke-subpages-1-Second_Page.html

A table with a header row and declared column widths, a block image with `align` and `width`, and a table cell holding two footnote markers.

The input is quoted in full in `corpus/smoke-subpages-1-Second_Page.html`; the two parts that matter are:

[source,html]
----
<colgroup>
<col style="width: 50%;" />
<col style="width: 50%;" />
</colgroup>
----

[source,html]
----
<div class="imageblock">
<div class="content">
<img src="{filepath}/1_" align="center" width="64" /></div>
</div>
----

pandoc, with the footnote `xref:` lines shortened:

[source,asciidoc]
----
[width="100%",cols="50%,50%",options="header",]
|===
|Column A |Column B
|Cell 1 a|
Cell 2^++[++^

[[__footnoteref_2]]
// two escaped xref: directives, as on the page above, omitted here

|===

image::{filepath}/1_[{filepath}/1++_++,width=64]

'''''

[[__footnotedef_2]]
[[_footnotedef_2]]
Footnote
// one escaped xref: directive omitted here
. A note belonging to the second page.
----

native, shortened the same way:

[source,asciidoc]
----
[cols="2*", options="header"]
|===

|Column A
|Column B

|Cell 1
a|
Cell 2 ^[^

[[__footnoteref_2]]
// two unescaped xref: directives omitted here
|===
 image::{filepath}/1_[]

'''

[[__footnotedef_2]]
Footnote
// one unescaped xref: directive omitted here
. A note belonging to the second page.
----

*The table. A tie here, pandoc in general.*
The two forms render byte-identical HTML, header row and 50/50 columns included, because `+cols="2*"+` and `cols="50%,50%"` mean the same thing for two columns.
They stop meaning the same thing the moment the widths are not equal: native measures the column count from the cells and discards `<col style="width: …">`, so a 30/70 table would come out 50/50.
The corpus has no such table, so this is a gap rather than an observed defect.

*The image. pandoc is right, and this one is the worst native defect.*
Native writes the image with a leading space.
An indented line is a literal block in AsciiDoc, so `asciidoctor` renders the markup as text:

[source,html]
----
<div class="literalblock">
<div class="content">
<pre>image::{filepath}/1_[]</pre>
</div>
</div>
----

The image does not appear at all, and the reader sees the directive instead.
`AdocOutput` already promotes a line-leading `image:` to `image::`, and it tolerates the indent while doing so, which is why the output looks almost right and renders wrongly.
pandoc also keeps `width=64`, which native drops along with `align=center`; pandoc's own blemish is that its escaping leaks into the alt text, `pass:[alt="1++_++"]`.

*Two footnote markers in one cell. Neither, but native breaks here.*
On this page native's links are not all sound:

[source,html]
----
href="../docToolchain_Confluence_Smoke_Test/Second_Page.html#<em>footnotedef_2"
href="../docToolchain_Confluence_Smoke_Test/First_Page.html#</em>footnotedef_1"
----

`AdocText` decides what to escape per HTML text node, and each of the two `<sup>` elements is a text node of its own holding one `+__+`.
Neither node contains a closing `+__+`, so neither is escaped - and then both land on the same output line, where `asciidoctor` pairs them up as unconstrained emphasis and eats them.
The escaping is decided per node and the markup is parsed per line, and the two disagree.

What native cannot do yet: block images, image attributes, non-uniform column widths, and escaping that accounts for what the neighbouring nodes will write on the same line.

=== smoke-subpages-1-First_Page.html

Everything from `smoke-subpages-2-First_Page.html`, plus an `<h1>` section heading and the code and admonition blocks of `smoke-subpages-2-Subsection.html`.
Only the heading is new, so only the heading is quoted:

[source,html]
----
<p>%%ANCHOR%%_subsection%%ANCHOR-END%%</p>
<h1 id="_subsection">Subsection</h1>
----

pandoc:

[source,asciidoc]
----
[[__subsection]]
[[_subsection]]
== Subsection
----

native:

[source,asciidoc]
----
[[__subsection]]
= Subsection
----

*pandoc is right.*
`writePage` puts `== <page title>` at the top of every exported document, so a heading in the body has to be `===` or deeper to sit inside the page.
Neither converter gets that right, but they are wrong by different amounts.
pandoc's `==` makes the subsection a sibling of the page title; native's `=` is a level-0 section, which outranks the page title and renders outside it:

[source,html]
----
<h2 id="_first_page">First Page</h2>     <!-- the page -->
<h1 id="__subsection" class="sect0">Subsection</h1>   <!-- native: above it -->
----

Everything else on this page repeats the three pages above: the dead pandoc footnote links, the broken native list, the missing space before `+_italic_+`, and identical admonition and listing blocks.

What native cannot do yet: map an HTML heading level to the document level the export actually writes at.

It is the sum of the five pages above and adds exactly one new observation, so the output is quoted only where it is new.

The heading hierarchy, rendered, with `== Page Title` prepended as the export writes it:

<!-- pandoc -->
<h2 id="_page_title">Page Title</h2>

The rest of this page differs exactly as the smaller pages do.

What native cannot do yet: every defect above, on a page where all of them occur at once.

== Summary

=== What the native converter already does better

*Links survive.*
This is the one difference that changes whether the export is usable - and it did not hold up against real pages; see the correction at the end of this document.
`fixBody` and `Footnotes` write real `xref:` directives into the HTML as text, and pandoc escapes them into prose: 12 `xref:` directives across the corpus, 0 of them a link.
Native writes the same 12, of which 8 render as links and 4 are corrupted by the escaping problem described under `smoke-subpages-1-Second_Page.html`.
Nothing in `AdocOutput` repairs the pandoc ones, so 0 against 8 is a defect in the shipping export that the PoC fixes by construction - not completely, but by an order of magnitude.

That count is about `xref:` text, which is how the corpus carries a cross-page link.
An `<a href>` element is a separate path, and the corpus has none: `rewriteLinksIntoThisExport` turns every in-export link into `<a href="X/Y.html">` and the `view-file` macro writes `<a href="…/1_spec.docx">` for an attachment, neither of which occurs in these six pages.
Both are now converted - `LinkSpec` is the evidence, not the corpus - and both used to be dropped: the converter required a `#` fragment and left a link without one as plain text, with its target gone.
pandoc keeps both targets, so this was a gap against pandoc and not a win until it was fixed.

*Code samples keep the characters they were written with.*
The body of a code macro reaches the document between `----` delimiters, where AsciiDoc substitutes nothing and strips no backslash.
Native escapes text for prose by default, which put a visible `+$\{HOME}+` in a shell sample; `NativeHtmlToAsciidoc` now marks the macro's listing block as `<pre>` and `PreformattedConverter` stops the escaping there.
pandoc escapes the sample either way - `+cp ++*++.txt+` - so this is a win rather than a repair, but only since the fix.
The corpus cannot show it: its one code sample is `+def hello = "world"+`, which has no character worth escaping.

*No escaping noise.*
`pass:[++_++]`, `pass:[++[++]` and `%7Bfilepath%7D` do not appear in native output at all.
The two repairs `AdocOutput` carries for them - the `%7Bfilepath%7D` rewrite and stripping pandoc's lone `pass:[+]` continuation lines, which occur 2 and 4 times in the corpus respectively - are dead code on the native path.

*No process.*
An export becomes a JRE and the jar, which is what publishing already is.
`ExportConverterChoiceSpec` is the proof: it runs a whole export and carries no pandoc guard, where `ExportConfluenceTaskSpec` skips itself without one.

*Tidier source.*
No blank lines inside listing blocks, one anchor per anchor instead of two.
Both render the same; it only makes the exported file easier to read and to diff.

=== What pandoc still does better

* *Lists.* Nesting. Both converters now render the title and every item; native writes a nested `ul` at its parent's level, which flattens the list.
* *Block images.* Native emits an indented `image::` line, which renders as a literal block showing the markup. The image is lost.
* *Image attributes.* `width` survives pandoc and not native; `align` survives neither.
* *Heading levels.* pandoc's `<h1>` -> `==` is wrong against the export's own `== <title>`, but native's `<h1>` -> `=` is worse: a level-0 section inside a page.
* *Spacing around punctuation.* Native drops the space after a comma that precedes an inline span, which changes the words on the page.
* *Declared column widths.* Native discards `<col style="width: …">`. No corpus table is affected, because all of them are equal-width.
* *Preserved line breaks.* `--wrap preserve` keeps one sentence per line; native joins the paragraph into one line.

=== Are the placeholder tokens still needed?

Mostly yes, which was not the expected answer.

The tokens exist because pandoc escapes AsciiDoc punctuation indiscriminately.
Native escapes selectively - `AdocText` asks what `asciidoctor` would do with the text unescaped - but a line of text that begins with `+[source, groovy]+` is a block attribute line to AsciiDoc, so `AdocText` escapes it on purpose and the token is needed just the same.
The same holds for `%%ANCHOR%%` (an `+[[id]]+` in text is an inline anchor), `+%%ADMON-*%%+` and `+%%EXPAND-*%%+` (delimiter lines), `%%TABLE-ROWHEADER%%` (an attribute line) and `%%CRLF%%` (a line break, which `BrConverter` writes as a space).

The measurement added one token rather than removing any.
`fixBody` used to turn a Confluence block title into a bare `+.Title+` line, which pandoc happens to leave alone - and which `AdocText` protects as text, because a line of prose beginning with a full stop would otherwise leave the page as a block title.
It now travels as `%%BLOCK-TITLE%%`, for exactly the reason the other tokens exist: AsciiDoc that the translation writes has to be told apart from text that the author wrote.

What the native path does make unnecessary is the pandoc *repairs* in `AdocOutput`, as counted above: the `%7Bfilepath%7D` rewrite and the removal of pandoc's lone `pass:[+]` lines.
Those two are the whole saving today.

The larger opportunity is that native makes the tokens avoidable rather than unnecessary: with a converter in process, `fixBody` could hand a real `<pre data-language="groovy">` to a `ListingConverter` instead of a string the next stage has to find again.
Half of that step is taken, and only on the native path: `NativeHtmlToAsciidoc` wraps the code macro's listing block in a `<pre>` before converting, which is what tells the converter not to escape the sample.
The other half - letting the `<pre>` carry the language and the delimiters, so that `%%SOURCE-BEGIN%%` and the `----` lines are not strings in the HTML at all - is a change to `MacroTranslator` that pandoc would have to survive too.
pandoc reads a `<pre>` as a block of its own and writes delimiters around it, so doing it in `fixBody` would nest one listing block inside another on the path that ships today.
That is why the marking sits in the native converter and not in the translation, and it is as far as this PoC goes.

=== What it would take to close the gap

In the order the corpus argues for, smallest first.

. *The indented `image::`.* `ImageConverter` writes a leading space it should not, or `AdocOutput` should trim the line it promotes to `image::` rather than tolerating the indent. One of the two, and the image is back.
. *Spacing after punctuation.* `TextNodeConverter` decides "does a space belong here" from a character whitelist, `+[a-zA-Z0-9.:/()]+`, that omits `,` and `;`. Honouring the text node's own trailing whitespace instead of re-deriving it would be the real fix.
. *Heading levels.* Both converters need to know the level the export writes the page title at. That argues for an option on the converter rather than a constant in it, since `writePage` is the only thing that knows.
. *Nested lists.* `ListConverter` and `ListItemConverter` need to carry a depth in the context, so that a list inside a list item writes `**` rather than `*`. This is the one the corpus shows most often.
. *Image attributes.* `width` and `align` are dropped by `ImageConverter`, which reads `src` only.
. *Column widths.* `TableConverter` measures the column count from the cells; it would have to read `<colgroup>` where one is present.
. *Escaping across node boundaries.* The `+__+` corruption needs `AdocText` to escape against the output line rather than against the text node. The context already carries what was written last, so the information is there; the decision is made in the wrong place.

None of these is architectural.
The seam is in place and either converter is one setting away, so each can be fixed and measured on its own.

== What the corpus cannot say

This comparison is only as broad as its input.
Absent from all six pages, and therefore not measured against pandoc here: `a`, `ol`, `pre`, `dl`, `blockquote`, `sub`, `h3`-`h6`, nested tables, `colspan`/`rowspan`, and the `%%STATUS%%`, `%%EXPAND%%`, `%%ADMON-TITLE%%`, `%%DISCRETE%%` and `%%TABLE-ROWHEADER%%` tokens.
`corpus/INVENTORY.md` records which of those have converters written against `asciidoctor` rather than against evidence.

Two of them are reached by the export on pages the corpus does not contain, which makes their absence worth more than the rest of the list.
`rewriteLinksIntoThisExport` and the `view-file` macro write an `<a href>` on every page that links to a sibling page or to an attachment; the code macro writes the `<pre>`-marked listing block whose content must not be escaped.
Neither is exercised by a corpus page, so both are specified directly instead - `link/LinkSpec` and `verbatim/PreformattedSpec` in the converter, `ExportConverterChoiceSpec` across the whole export.
A spec is weaker evidence than an exported page, and the right answer is still to export a page that has them.

Closing that gap means exporting a page that has them, not writing more HTML by hand.

== Measured again, against real pages

Everything above was measured against the corpus: six pages, derived from this project's own golden files.
The export was then run against 43 pages of the ASF `MAVEN` space (root page 2853526, "Maven 3.x", read-only, attachments off), once with each converter.
What that showed matters more than the corpus did, and it contradicts the corpus on the one point that had looked decisive.

=== The link finding does not survive

On the corpus, pandoc escaped all 12 `xref:` directives into prose and native kept 8 of them.
On 43 real pages both converters wrote **52** `xref:` directives and each corrupted exactly **one**.

The corpus has `xref:` only where `fixBody` writes one into the HTML as text, and three of its six pages carry footnote cross-references, which is a density no real page has.
So the 0-against-8 was an artefact of the input, not a property of pandoc.
The claim above is left standing with this correction beside it rather than quietly edited, because the measurement that produced it was honest and the conclusion drawn from it was not.

=== What the real pages showed instead

Native is not better than pandoc here.
It is wrong in different places, and two of its differences change the words on the page:

* *A missing space before a link.* `…GenericVersion.java[…]in link:…` - the text node's trailing whitespace is dropped, which is gap 2 above, seen in prose rather than in a fixture.
* *Bold becomes a literal asterisk.* `issue tracked as *https://…[MNG-3010]*` turns into `* link:https://…[MNG-3010]*`: the opening `*` is separated from its text, so the span is not bold any more and a stray asterisk is on the page. That is gap 7.
* *Heading levels.* `== Improve default support for version schemes` from pandoc, `= Improve …` from native - a level-0 section inside a page that is included elsewhere. Gap 3, and these pages are full of it.
* *AsciiDoc attributes for characters that need them.* pandoc writes `{nbsp}` and `{plus}`; native leaves a literal no-break space and writes a bare `+`, which AsciiDoc reads as markup.
* *Redundant `link:`.* Native writes `link:https://…[text]` where pandoc writes `https://…[text]`. Both render; only the diff is noisier.

=== Two macros the corpus never contained

The run reported 111 `ac:emoticon` and 15 `ac:structured-macro noformat`, neither of which occurs in the corpus and both of which the translation drops with only a count.
An emoticon is probably not worth carrying across; a `noformat` block is a code block without a language and is.
Both are translation work in `MacroTranslator`, not converter work, and neither is affected by which converter runs.

=== Timing

pandoc 20.9 s, native 18.9 s, for the same 43 pages.
As predicted from the per-invocation measurement recorded in the decisions, the conversion is not what an export spends its time on: three REST requests per page are.
Replacing pandoc buys about two seconds in twenty, and the argument for it has to stand on the other grounds.
