= Design decisions
:toc: left
:icons: font

Decisions taken while extracting Confluence support from docToolchain, newest last.
Each entry records what was decided and, more importantly, why.

== Build with Maven, not Gradle

docToolchain builds with Gradle, this project does not.
Maven is the ecosystem the primary users live in: the first target is a Confluence Data Center customer whose projects are Maven projects.
Building with Maven also makes the Maven plugin a natural module rather than a foreign body.

A Gradle plugin remains possible later.
docToolchain can equally consume the plain library and keep its own task definitions, which would make a Gradle plugin unnecessary.

== Java for production code, Spock for tests

Production code is Java, compiled with JDK 25 and released for Java 17.

The moved code is Groovy and is ported class by class, bottom up.
Ported that way, Groovy classes reference Java classes and never the reverse, so `maven-compiler-plugin` can simply run before `gmavenplus-plugin` and no stub generation is needed.

Tests stay on Spock for the duration of the port, so the suite keeps verifying every ported class.
Two measured constraints shape the versions:

* Groovy 3.0.13, which docToolchain pins, cannot compile on JDK 25 ("Unsupported class file major version 69").
* Spock has no Groovy 5 build, so Groovy is capped at 4.x for as long as Spock is used.

== YAML as the primary configuration format, TOML shipped alongside

docToolchain configures itself through `docToolchainConfig.groovy`, which `ConfigSlurper` *executes*.
That file is code, not data.
Anyone able to supply it can run arbitrary code in the build, and it ties the configuration to Groovy, which blocks the Java port.

The configuration is therefore a typed model bound by Jackson.
YAML is the primary format because `confluence.input` is a list of records, which YAML expresses in two lines while TOML needs array-of-tables.
TOML and JSON come from the same model at the cost of one line in the loader.

Secrets never belong in the configuration file.
Resolution order is command line argument, then environment variable, then file, then default.

docToolchain keeps its `ConfigSlurper` and maps its `ConfigObject` onto the typed model, so existing users change nothing.

== Legacy configuration options are dropped

`allInOnePage` and `createSubpages` were superseded by `subpagesForSections` in docToolchain and are still read there.
They are not carried into the typed model.

== Package names are kept

Packages stay at `org.docToolchain.atlassian.confluence` and friends, unchanged from docToolchain, so that Jira can be extracted along the same path later.

Maven coordinates are lowercase throughout (`org.doctoolchain:dtc-confluence`).
GitHub Packages rejects uppercase, even though Maven Central accepts it.

== Transformation stays independent of the API

The classes under `atlassian.transformer` turn markup into markup.
They must not depend on `confluence.clients`, so they stay testable without any HTTP in sight, and so a future producer of storage format can reuse them without dragging a REST client along.

== Packages stay free of cycles

The Groovy code is being ported to Java one package at a time, bottom up.
That only works while the dependency graph is acyclic: a cycle would force two packages to move together, and the port would stop being decomposable.

Every package is its own slice, which is stricter than slicing by top-level sub-package.

== An Asciidoctor backend: considered, deferred, interface kept open

Today the pipeline is `AsciiDoc -> asciidoctor(html5) -> HTML -> Jsoup -> storage format`.
The middle step reconstructs semantics from CSS classes: `div.sect1`, `div.sect2`, `.title`, `.content`, `div#preamble`, `div.arc42help`.
Information that existed in the AsciiDoc AST (admonition kind, block title, source language, cross-reference target) is flattened into HTML and scraped back out.

Writing an Asciidoctor converter that emits Confluence storage format directly would remove that whole class of defects.
The mangled block title (`<strong><br/><div><div class="title">`) exists only because the title has to be rediscovered as `div.title`.
The scraping is also silently coupled to Asciidoctor's HTML markup, which changes between releases without any test noticing.

Deferred, for three reasons:

* An AsciidoctorJ converter drags JRuby into the library. The core has no Asciidoctor dependency at all today, which keeps it small for CI use.
* A converter emits one string per node, while publishing produces a *tree* of pages driven by `subpagesForSections`. That is buildable but is not the converter API's normal path.
* The HTML path cannot be retired anyway: `inputHtmlFolder` and `url` inputs accept HTML that Asciidoctor never produced.

=== What it would and would not buy for round-trips

Measured against ASF Confluence DC 9.2.21:

* Publishing an unchanged source is already idempotent. The content hash suppresses the write, the page version does not move, and inline comments survive untouched.
* Inline comments live *inside* the page body as `<ac:inline-comment-marker ac:ref="...">text</ac:inline-comment-marker>`.
* When a page does change, publishing replaces the whole body. The marker is gone, and while the comment object survives, its anchor does not.

A better backend does not fix this on its own, because the loss comes from full body replacement, not from the HTML detour.
Preserving inline comments needs an explicit merge: read the current storage format, extract the markers, and re-apply them to the newly generated body.

The backend makes that merge *tractable* rather than unnecessary, because stable, semantically faithful output is what lets markers be matched reliably.

=== Consequence for the ongoing port

The core must take a **page tree** - titles, storage-format bodies, ancestors, attachments, labels - not an HTML file.
Today that model is tangled together with the Jsoup scraping inside `Asciidoc2ConfluenceTask`.
Separating the two is what makes those 823 lines portable in pieces, and it is the same seam a converter would later plug into as an additional producer.

== Idea: partial updates that preserve inline comments

Not planned for a particular release, recorded so the reasoning is not redone.

Confluence offers no partial update.
`PUT /rest/api/content/{id}` replaces the body wholesale; there is no section-level patch in the Data Center v1 API.
"Partial" therefore has to be a client-side merge.

Publishing already skips unchanged pages by content hash, so page-level granularity exists.
The gap is *within* a page that genuinely changed.

The merge would be:

. Read the current storage format of the page.
. Extract the `ac:inline-comment-marker` elements with their anchored text and surrounding context.
. Generate the new body as today.
. Re-wrap the anchored text in the new body, where it still exists.
. Report the markers that could not be placed, instead of losing them silently.

The plumbing is already in place: `fetchPageByPageId` expands `body.storage`, and the publisher already compares against the remote body before deciding to update.
No extra API round trip is needed.

Two things make this harder than it looks:

* Anchored text is not necessarily unique on a page, so context is needed to pick the right occurrence.
* An anchor may span inline markup, in which case the marker is already split across elements in the stored body.

A useful distinction for scoping this: inline comments are *annotations on* generated content, whereas an edited paragraph or a ticked task box is an *edit of* it.
For a publishing tool the generated source stays authoritative, so edits are meant to be overwritten.
Annotations are not, and that is what makes comments worth the merge.

== Content hashes keep the platform default charset

`ContentHash.md5` hashes `text.getBytes()` without naming a charset, so the result depends on the platform default.
That is inherited, not chosen: the Groovy it replaces used `s.bytes`, which does the same.

It is worth knowing that this makes hashes machine-dependent.
The same document hashed on a UTF-8 developer machine and on a CI runner with a different default produces different hashes, and every page and attachment would be rewritten once.
Attachments are affected twice over, because their content is read as text before being hashed, which mangles binary files on the way.

Changing it to UTF-8 would be correct and would cost one rewrite of everything ever published by docToolchain.
That is a decision with a migration attached, not a detail to fix inside a port.

== Collapsible blocks lose their fold

AsciiDoc marks a block collapsible with `[%collapsible]`, and Asciidoctor renders that as `details` with a `summary`.
Neither survives: the elements are unwrapped, the summary is left as bare text with no markup at all, and the content stands open on the page.

arc42 templates lean on collapsible blocks for guidance text, so an arc42 document published today carries every hint it meant to hide.

The publisher can already produce the macro that would fix this:

[source,groovy]
----
body.select('div.arc42help').select('.content')
    .wrap('<ac:structured-macro ac:name="expand"></ac:structured-macro>')
----

It applies that only to `div.arc42help`, a class from one particular template, while the language's own `[%collapsible]` runs past it.
That is a gap rather than a decision: the same effect, supported through one spelling and dropped through the other.

Mapping `details` onto the `expand` macro is the fix: the `summary` becomes the macro title and the rest its rich text body.
`[%collapsible%open]` has no equivalent - a Confluence expand macro is always folded - which is a loss worth accepting rather than a reason to leave the rest broken.

== Callouts in code blocks: three ways, chosen by configuration

A callout marker inside a Confluence code macro cannot be both visible and absent from the clipboard.
The macro holds plain text, where what is shown and what is copied are the same field.
Asciidoctor's HTML has no such constraint: it generates the marker with `::after` and hides the literal one, so a browser copies clean code.

This matters most with line continuations.
In a shell, a continuation and a trailing comment are mutually exclusive - the backslash has to be the last character on the line - so a copied block with markers does not run.
That is a property of the shell, not of Confluence, and no amount of escaping fixes it.

Three handlings, to be selected in the configuration rather than argued about:

`comment`:: The default. The marker becomes a comment in the code: `+# (1)+` in a shell, `+// (1)+` in Java.
Keeps the marker beside its line, at the cost of copyability.
The comment character follows the language - `+#+` for shell, Python, YAML and Perl, `+--+` for SQL and AppleScript, `+<!-- -->+` for XML, `+/* */+` for CSS.
docToolchain wrote `+//+` into every one of them, and a marker the language does not ignore defeats its own purpose.
`expand`:: The annotated block is published as it is, and a second copy without markers follows it inside a collapsed `expand` macro.
Nothing is lost, at the cost of every affected block appearing twice.
`linenumbers`:: The markers are left out of the code entirely and the macro is given `linenumbers=true`, so the callout list can refer to line numbers.
The code stays copyable character for character; the markers no longer sit beside their lines.

`comment` stays the default, because changing what existing users publish should be their decision rather than an upgrade's.

A callout directly after a line continuation in a shell-like language produces a block that cannot be run, and the author is unlikely to notice from the source.
Such a block is published with a collapsed copy without markers underneath it whatever the setting says, and warned about - with one exception: `linenumbers` already leaves the block runnable, so there is nothing there to warn about.

Only an odd run of trailing backslashes counts.
Two of them are an escaped backslash and the line ends there, so a marker behind those is an ordinary comment.

All three need the same building block as the collapsible fix above, which is a reason to do that one first.

== Footnotes follow their reference; one in a heading is lost

Asciidoctor collects footnote definitions in a `div#footnotes` at the end of the document.
That div is a sibling of `div#content`, not a child, so page splitting never read it and the published references pointed at definitions that had been left behind.

A definition now travels to the first page that refers to it.
References on later pages resolve through the anchor map and link across, so a definition is written once and Asciidoctor's document-wide numbering keeps its meaning: numbers do not restart per page.

A footnote in a *section heading* cannot be carried over.
The heading becomes the Confluence page title, and a page title is plain text - there is no body for a reference to point into.
The reference is dropped, and because nothing on any page then refers to that definition, it is not published either.
The page stays self-consistent; the footnote is simply gone.

The number is stripped from the title rather than left in it, because it would otherwise turn `Architecture` into `Architecture1` - and since the title also decides page identity, adding a footnote to a heading would rename the page and orphan the old one.

Carrying such a footnote into the page body was considered and rejected for now: it would have to appear somewhere the author did not write it, and no placement is obviously right.
== The export needs pandoc; the publisher does not

The conversion from Confluence storage format back to AsciiDoc does not do the conversion itself.
It prepares the XHTML, hands it to `pandoc`, and post-processes what comes back.

That is inherited from docToolchain and is worth stating plainly, because it makes the two directions unequal:

* publishing is a jar and a Java runtime, nothing else
* exporting additionally requires pandoc on the `PATH`

Porting the converter to Java does not change this - it would replace the code around pandoc, not pandoc.
Writing a storage-format-to-AsciiDoc converter from scratch is a different project, and a large one.

Keeping pandoc is the decision for now.
The export is the smaller half of what people ask this tool for, the dependency is well-known and packaged everywhere, and docToolchain has required it for years.
What changes is that it is now documented rather than discovered when a build fails.

The alternative remains open: should the export become as important as publishing, the pandoc step is one method, and a Java implementation can replace it behind the same interface.

== The export drivers carry a second HTTP stack

`confluenceApiToAsciiDoc.groovy` talks to Confluence through `HttpURLConnection`, opened and configured by hand: authentication, redirects, paging and attachment downloads are all re-implemented there.

This project already has `RestClient`, built on Apache HttpClient 5, which does the same things for publishing - bearer and basic authentication, the rate limit, the proxy, JSON parsing, and the error handling that says what went wrong.

Carrying both would mean two places to fix every authentication or proxy problem, and two behaviours for the same configuration.
The driver is therefore to be rewritten onto the existing client rather than moved across as it stands.

That is a rewrite, not a move, so it does not share the safety of the converter port: there the closures became methods with the behaviour untouched, and the characterisation tests mean something.
Here the tests have to be written against what the driver produces - the pages, attachments and space maps the converter expects - before the fetching underneath them changes.
== An explicit `false` is not the same as an unset value

`ConfigService.getConfigProperty` mirrors Groovy truth, which the original implementation relied on: an empty map, an empty string, a zero and a `false` all answer `null`.

Everywhere the question is only "is this switched on?" that is harmless.
It stops being harmless where a default is applied only when nothing was configured - `confluence.useV1Api = false` then reads as "nobody said", and the derived value silently overrides what the author wrote.

`getRawConfigProperty` answers without applying Groovy truth, and is what such a decision has to use.
The distinction is worth keeping in mind for the typed configuration: it disappears there, which is one more reason to want it.

== Page titles are unique per space, so keying by title is safe on Data Center

`fetchPagesBySpaceKey` collects pages into a map keyed by the lower-cased title, and `wipe` deletes what that map holds.
A review raised this as a defect: if Confluence only guaranteed titles to be unique among siblings, two pages could collide in that map and one would never be deleted, while a command that promises to delete every page said it had.

Measured against Confluence Data Center 9.2.21, creating a page whose title already exists elsewhere in the space:

[source]
----
HTTP 400 - A page already exists with the title "..." in the space
----

The parent does not matter; the space does.
The premise is therefore wrong for Data Center, and the title-keyed map holds every page.

Two things follow.
It is the reason page identity in this project is the title at all - and the reason renaming a heading creates a page rather than moving one.
And it is a Data Center guarantee: Cloud has not been verified here, and if it ever allows two pages of one title, the wipe path needs a listing keyed by id rather than a rewrite of the one publishing shares.

== A manifest of what was published (idea, not decided)

The publisher already fingerprints a page: it writes `hash: #...#` into an `ac:placeholder` and compares it on the next run, which is what "page hasn't changed!" means.
That fingerprint lives *in Confluence*, so answering "what would this publish change?" requires asking Confluence first.

The idea is a file in the repository recording, per source file, what was published from it: the page id, the content hash, and which revision produced it.

=== What it would be worth

The strongest argument is not change tracking.
It is *page identity*.

Today a page is identified by its title, because Confluence keeps titles unique per space - measured, see above.
That makes renaming a heading indistinguishable from writing a new section: the publisher creates a second page and orphans the first, and the author usually notices weeks later.
A manifest mapping a source file to the page id it produced would end that: a renamed heading becomes an update, not a stranger.

Two smaller gains follow.
Drift becomes visible - a page edited by hand in Confluence has a hash that no longer matches the recorded one, which today nothing reports.
And a dry run becomes possible offline: what this revision would change can be answered without credentials.

=== What it would cost

A committed manifest is shared mutable state that every branch writes to, so every publish from a branch is a merge conflict waiting for the next one.
One line per page, sorted, keeps those conflicts small and mechanical, but they do not go away.

It also introduces a second source of truth beside the hash already in Confluence, and the two can disagree - after a restore from backup, after a space copy, after publishing from a second machine.
Whichever is believed has to be stated, and the honest answer is that Confluence wins: it is where the page actually is.
The manifest is then a cache, and saying so avoids pretending it is a ledger.

Per-branch publishing complicates it further, because `pagePrefix` and `pageSuffix` already exist so that one document can be published several times into one space.
A manifest would have to be keyed by those too, or be per-target rather than per-source.

=== Where that leaves it

Worth building for page identity, which is a real defect with no other fix in sight.
Not worth building for change tracking alone, which the hash in the page already does.

If it is built: written always, committed by choice, keyed by target rather than by source file, and documented as a cache that Confluence overrules.
