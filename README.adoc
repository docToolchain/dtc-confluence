= dtc-confluence
:toc: left
:icons: font

Confluence support for docs-as-code, extracted from https://doctoolchain.org[docToolchain].

The project publishes AsciiDoctor-generated HTML to Confluence and exports Confluence content back to AsciiDoc.
It is usable as a plain library and, on top of that, through a CLI and a Maven plugin.

== Status

Early.
`dtc-confluence-core` is a move of the Confluence code from docToolchain 3.4.2.
That code is Groovy and is being ported to Java class by class; the Spock test suite stays in place throughout to verify each step.
`dtc-confluence-cli` runs the publisher without a build tool and is usable today, against Confluence Data Center.

== Modules

`dtc-confluence-core`:: The library, with no binding to any build tool.
`dtc-confluence-cli`:: Command line tool.
`dtc-confluence-maven-plugin`:: Maven integration (planned).

== Supported Confluence versions

Confluence Data Center 9.2:: Primary target, tested against a real instance.
Uses REST API v1 under `/rest/api`.
Confluence Cloud:: Through REST API v2 under `/api/v2`.
Present, but not yet verified against a real instance.

[NOTE]
====
REST API v2 exists in Cloud only.
On Data Center `/api/v2` answers with 404, and v1 is the single, undeprecated option there.
====

== Installing the command line tool

Build it, then install from the directory the build lays out:

[source,bash]
----
./mvnw package
./dtc-confluence-cli/target/install/install.sh
----

That copies the launcher to `$HOME/.local/bin/dtc-confluence` and the jar below `$HOME/.local/lib`.
Pass `--prefix DIR` to install elsewhere, `--force` to replace an existing installation.
Nothing outside the prefix is touched, so removing those two paths uninstalls it.

`dtc-confluence-cli/target/install.zip` holds the same layout for copying to another machine; the launcher runs from the unpacked directory without installing.

Running it needs a Java runtime of version 17 or newer, which the launcher looks for in `JAVA_HOME` and then on the `PATH`.

== Using the command line tool

Start with a configuration:

[source,bash]
----
dtc-confluence init --api https://confluence.example.com --space SPACEKEY
----

That writes `.dtc-confluence.yaml` - hidden, because it configures the tool rather than describing the documentation.
It is also the first name looked for when no `--config` is given; `.dtc-confluence.yml`, `dtc-confluence.yaml`, `dtc-confluence.yml` and finally docToolchain's `docToolchainConfig.groovy` follow, so an existing docToolchain project keeps working unconverted.

[source,bash]
----
# Read the token from wherever you keep it, rather than typing it:
export CONFLUENCE_BEARER_TOKEN=$(pass show confluence/token)   # or op, gopass, security...

dtc-confluence verify  -d docs        # check URL and credentials
dtc-confluence publish -d docs --dry-run   # say what would change, write nothing
dtc-confluence publish -d docs        # publish the configured inputs
----

A dry run (`-n`) reads everything a real run reads and writes nothing.
It reports one line per page - `would create`, `would update` (with the version it would write), `unchanged` (the page already carries the hash of this text), `would fail` (a page of that title exists under another parent, which Confluence refuses) - and ends with a count.
Attachments and labels are not compared: they are written after the page they belong to, so a dry run only says how many would travel with a new page.

`would fail` is the case worth knowing about, because a Confluence title is unique per space: a page of that title already exists somewhere else in the space, so the new one cannot be created beside it.
The report says where that page hangs, links to it, and says whether this publisher wrote it - a page carrying the hash of an earlier run is almost certainly the same page, moved or renamed since.
For that case `--move` (`confluence.moveExistingPages`) writes it back under the parent this document asks for, instead of failing.
A page without that hash was written by somebody else and is never moved; rename the heading or set `confluence.pagePrefix` to keep the titles apart.

The other half of the same defect is a heading that *was* renamed: the new title creates a new page and the old one stays where it was, so the space ends up holding both.
Every run - dry or not - now names the pages below the document that an earlier run wrote and this one did not touch, with a link to each.
They are not deleted: what to do with them is a decision, and this tool is not the one to take it.
Both halves go away once a page is identified by its id rather than by its title, which is what xref:docs/decisions.adoc[the publish manifest] is for.

Attachments are published under the name Confluence knows them by.
An export writes a file as `<version>_<name>`, because a document may refer to an older revision of a diagram; that prefix stays on disk, and the attachment goes back as `diagram.png`.
The version it names is what answers the question that decides whether to write at all: Confluence still holding exactly the revision the export came from means nobody has written it since.
Where somebody has - the draw.io app writes its own version comment, which no content hash can recognise - the run says so and writes nothing:

[source,yaml]
----
confluence:
  foreignAttachments: fail   # fail (the default), skip, or overwrite
----

`--foreign-attachments` says the same on the command line.
An attachment created in Confluence that no export ever saw, and that no run of this publisher wrote, is left alone under every setting but `overwrite`: unknown means not ours.

The prefix is dropped only where the shorter name stays unique on that page.
Two revisions of one picture shown side by side - and screenshots an author numbered `01_step.png`, `02_step.png` - keep the names the document refers to, because one attachment cannot be two pictures; the run names the files it did that for.
A name that Confluence holds with a space, a colon or a path separator in it does not survive the round trip at all: the export replaces those characters with `_`, so `my diagram.png` comes back as a second attachment called `my_diagram.png` rather than as a new revision of the original.
A picture that carries a draw.io diagram is published as that diagram.
draw.io keeps its own source inside what it exports - a PNG in a text chunk, an SVG in a `content` attribute - so one line of AsciiDoc means two things, and the file decides which:

[source,asciidoc]
----
image::architecture-context.png[System Context,700]   // carries its source: an editable diagram
image::architecture-flat.png[System Context,700]       // exported without it: a picture
----

The diagram is attached under the picture's base name with no extension, which is how the app binds one, and the picture beside it as `<name>.png`, which is the preview a PDF export shows.
An SVG carrying a diagram needs the PNG of the same name beside it to be that preview; without one it stays a picture, and the run says so.
There is nothing to configure, and nothing happens to a picture that carries no diagram.

A name Confluence holds with a space, a colon or a path separator in it is not written to disk as it is - the last of those would reach into another directory - so the export replaces those characters with `_` and the document refers to `my_diagram.png`.
Published under that name it would be a second attachment beside the original rather than a new revision of it.
The name is therefore matched against what the page holds before the reference is written, and the file goes back under the name Confluence knows:

[source,yaml]
----
confluence:
  resolveAttachmentNames: true   # the default; false publishes the name the document uses
----

`--resolve-attachment-names` and `--no-resolve-attachment-names` say the same on the command line.
It is a lookup rather than a calculation, because `my_diagram.png` is a legal attachment name of its own and guessing which `_` was once a space would write over a file nobody named.
Where a page holds two attachments that the export writes under one name, the run says which two and publishes the name the document uses, since only the author can tell them apart.
It costs one request per page that already exists and has attachments to publish.

`CONFLUENCE_CREDENTIALS=user:token` is the alternative where the instance wants basic authentication.

Credentials are read from the environment rather than taken as options, which keeps them out of the process arguments - `ps` shows a command line to every user on the machine.
It does not keep them out of your shell history: a token typed into an interactive `export` is recorded there like anything else, which is why the example reads it from a secret store instead.

The other way round, `export` fetches a page and everything below it and writes AsciiDoc:

[source,bash]
----
dtc-confluence export -d docs    # needs pandoc on the PATH
----

It reads its settings from `confluence.export`:

[source,yaml]
----
confluence:
  export:
    destDir: build/confluence-export   # relative to --doc-dir
    rootPageId: '451974352'            # or rootPageTitle: 'The page to start at'
    downloadAttachments: true          # the default
    stripChapterNumbering: true        # "5.2.4. Title" becomes "Title"
    stripPagePrefixRegex: ''           # shortens file names, e.g. '^PROJ_'
----

Below `destDir` it writes `docs/` with one file per page in folders mirroring the page tree, `docs/images/` with the attachments, and the `_menu.adoc` and `_config.adoc` a microsite reads.

Each page also carries the `include::` lines for its children, wrapped in `ifdef::includeChildren[]`, so that a page can be read on its own or as the root of its subtree - set `includeChildren` to pull the subtree in.
Each page's title is written as `= Title`, the document title, so that the file reads on its own; each step down the tree places the included page a level deeper.
AsciiDoc has six heading levels, and they still run out on a deep tree: a page five steps below the root carries its title at the last of them, and a page's own headings start below its title, so a tree three pages deep has three levels left for the deepest page's body.
Past that the headings stop being headings, and nothing reports it.
The limit and what it cost to push it out by one are written down in xref:docs/decisions.adoc[the design decisions].
A draw.io diagram comes back as one file: the export puts the `mxfile` inside the preview, so the picture in the repository is also the diagram, and publishing that document again writes the macro back rather than a flat picture.
The source is read from the `mxfile` and never out of the preview, because a preview is derived and may be older than what it derives from.
Where it is - the app keeps the default view's preview current and lets a pinned view's go stale - the run says which view, and draws it again only if draw.io happens to be on the `PATH` and says it is 27.0.2 or newer, which is where it began numbering pages from one.
The exported file carries the current diagram either way, so what can be out of date is the picture inside it and not the source.

Publishing needs a JRE and the jar; exporting needs pandoc as well, because the conversion back to AsciiDoc goes through it.
draw.io is never needed, in either direction.

The last command, `wipe`, deletes every page in the configured space and refuses to run without `--yes-delete-every-page`.

== Building

[source,bash]
----
./mvnw verify
----

Builds with JDK 25, targets Java 17.
Maven comes from the bundled wrapper, so no local Maven installation is required.

== External tools

Two programs are called as processes rather than used as libraries, and both are pinned to an exact version in CI.

pandoc:: Needed to export.
`ConfluenceConverter` runs it over each page's prepared XHTML, so pandoc is what actually writes the AsciiDoc this project produces.
Publishing does not need it.
asciidoctor:: Needed only to run the whole test suite.
Nothing under `src/main` calls it.
Two specifications use it as an oracle, to answer whether the AsciiDoc this project emits reads the way it is meant to - whether a block is read as markup, and whether an include lands a level deeper.
Without it, those two skip themselves.

=== Why they are pinned

Because their output is the behaviour under test, not an incidental property of the machine that happens to run it.

pandoc writes the output, so its version decides what the assertions about escaping are compared against.
asciidoctor judges the output, and an oracle whose version drifts is an oracle whose verdict drifts.
A build that passes at one desk and fails at another, for no reason in the code, is worse than a build that simply fails.

CI installed both from apt until recently, which gave pandoc 3.1.3 (June 2023) and asciidoctor 2.0.20 (May 2023) against the 3.12.1 (October 2026) and 2.0.26 used in development.
The assertions about what pandoc escapes were therefore being checked against a pandoc three years older than the one that wrote their fixtures.
Both now come from a pinned release, pandoc verified against a checksum.

`.github/workflows/tool-versions.yml` reports once a week when either has moved upstream.
The bump itself stays a decision a person makes, because it changes what the specifications assert.

=== Asciidoctor is not a dependency of this project

docToolchain embeds Asciidoctor as a library, through asciidoctorj and JRuby, because it renders AsciiDoc.
This project does not render AsciiDoc; it produces it.
There is no Asciidoctor on the class path and no `asciidoctorj` in any `pom.xml`, and the version that verifies the output is chosen here rather than inherited from whatever consumes it.
A renderer that a consumer happens to ship must not decide whether these specifications pass.

== Linting

The build does not lint workflows, YAML, XML or shell scripts; CI does, through super-linter.
To run the same checks before pushing:

[source,bash]
----
./tools/lint.sh
----

It calls the tools directly rather than through super-linter, which publishes no arm64 image and takes minutes to start under emulation.
The configuration files are shared with CI, so findings match.
Tools that are not installed are reported and skipped.
